# Unverified Claims and Remaining Uncertainties

## 1) Claims that remain unverified or only partially verifiable

1. **Точні бюджети тренування конкретних комерційних моделей (наприклад “GPT-4 > $100M”, “Midjourney $5–10M”, “Stable Diffusion $10–15M”).**  
   - Статус: частково верифіковано лише як оцінки зі сторонніх аналітичних джерел.  
   - Проблема: відсутня повна офіційна фінансова розбивка від вендорів.

2. **Точна архітектура Midjourney по версіях (v1–v6).**  
   - Статус: непідтверджено.  
   - Проблема: немає peer-reviewed або офіційного технічного whitepaper з повною специфікацією.

3. **Внутрішні реалізації “standard voice” vs “advanced voice” у ChatGPT як строго ASR→LLM→TTS або end-to-end у всіх режимах/версіях.**  
   - Статус: частково верифіковано на рівні продуктового опису, але не повністю на рівні внутрішньої архітектури.

4. **Універсальні кількісні правила для steps (наприклад “X scheduler завжди якісний за 10–30”).**  
   - Статус: неповна верифікація як загальне правило.  
   - Проблема: сильно залежить від checkpoint, задачі, CFG, resolution і цільової метрики.

5. **Твердження про “однакову пам'ять” для довжелезних контекстів у Mamba-типах.**  
   - Статус: частково верифіковано на рівні асимптотичних властивостей; не універсально для будь-якої реалізації та hardware.

## 2) Source availability notes

1. Частина посилань з лекційного матеріалу веде на:
   - блоги / соціальні мережі / third-party огляди;
   - сторінки без повної технічної специфікації;
   - комерційні ресурси без методологічної деталізації.

2. Для деяких тверджень немає прямого первинного джерела (paper або офіційний технічний документ), тому вони позначені як:
   - **engineering practice**, або
   - **best-effort estimate**, або
   - **unverified claim**.

## 3) Remaining uncertainties for manual instructor review

1. Які саме оцінки бюджету тренування приймати як “офіційні” в межах курсу (лише vendor statements чи також аналітичні оцінки).
2. Чи включати в основний текст порівняння закритих систем (Midjourney, proprietary voice pipelines) як ілюстрації, чи переносити їх в окремий “непідтверджений/оглядовий” блок.
3. Який рівень математичної глибини expected для студентів у частині ODE/SDE інтерпретації scheduler-ів (базовий чи розширений).

---

## 4) Practical recommendation

Для наступних версій лекції варто маркувати твердження в тексті тегами:

- **[FACT]** — підтверджено paper/official docs;
- **[PRACTICE]** — усталена інженерна практика;
- **[ESTIMATE]** — оціночні цифри;
- **[UNVERIFIED]** — немає надійного підтвердження.

Це зробить матеріал прозорішим для студентів і зменшить ризик сприйняття припущень як фактів.
